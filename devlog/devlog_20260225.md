### 2. engine.py Guardrail 로직 수정 (핵심)

**문제**: 인포그래픽(viewer.py)과 실데이터 검증(engine.py)의 Guardrail 로직이 근본적으로 달랐음.

| | engine.py (구) | viewer.py 인포그래픽 | engine.py (신) |
|--|---------------|---------------------|---------------|
| 인출 시도액 | `W0 * init_wr / 12` (고정, 불변) | `W[t]` (이전 달 인출액) | `prev_withdraw` (이전 달 인출액) |
| 밴드 기준 | 연환산 인출률 (WR) | W/NAV 월비율 | W/NAV 월비율 |
| 밴드 내 동작 | 항상 고정 base로 복귀 | 이전 인출액 유지 | 이전 인출액 유지 |
| Upper cap | `upper_wr * NAV / 12` | `upper_ratio * NAV` | `upper_ratio * NAV` |
| Cap 후 기준 | 다음 달 다시 고정 base | 조정된 금액이 다음 달 기준 | 조정된 금액이 다음 달 기준 |

**증상**:
- engine.py(구): band=5%에서 Upper cap이 79% 발동 → Fixed와 거의 동일
- viewer.py: Upper 32회, Lower 70회, 밴드내 138회 → 진정한 동적 인출

**원인**: engine.py가 매월 고정 base로 리셋하여, NAV < 95.2이면 항상 Upper cap 발동

**수정 함수**:
- `simulate_withdrawal_on_path` (scalar, line 170)
- `simulate_withdrawal_on_paths_vectorized` (numpy, line 611)

**검증**:
- engine.py vs viewer.py 인포그래픽: NAV/인출액 max_diff = 0.00 (완벽 일치)
- 벡터화 vs scalar: max_diff = 0.00
- 기존 테스트 1~3, 5~7: 모두 통과

## 핵심 교훈

Guardrail의 본질은 "이전 인출액을 유지하되, 비율이 밴드를 벗어나면 조정"하는 것.
매월 고정 base로 리셋하면 band가 아무리 좁아도 NAV 변동 시 항상 cap이 발동하여
사실상 Fixed와 동일해진다. 이전 인출액 carry-forward가 핵심.
